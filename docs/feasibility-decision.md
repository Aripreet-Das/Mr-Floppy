# Feasibility Decision Record

## Decision
**NO** — virtual-source emulation is not feasible as a supported migration source pathway at setup time.

## Technical Rationale

The desktop app cannot satisfy the three gates that stock Samsung/Android setup-time flows impose on a source device:

1. **USB Gadget ADB Function** — The destination device enumerates connected USB functions and requires the `android.adb` function configuration (`bInterfaceClass 0x03, bInterfaceSubClass 0x01, bInterfaceProtocol 0x01`). A Tauri/Rust desktop app running on macOS/Windows cannot instantiate a USB gadget function; this requires kernel-level `g_android` binding on the host, which is not available outside the target device itself.

2. **DeviceSetupToken** — `DeviceSetupManager` (`packages/apps/Settings/src/com/android/settings/device/setup/DeviceSetupManager.java`) enforces that any device claiming the source role present a valid `DeviceSetupToken`. This token is generated by the destination's embedded setup wizard after a proprietary attestation handshake involving the device's eFUSE keys. The desktop app has no pathway to obtain or forge this token.

3. **Proprietary Credential Handshake** — The setup flow performs a challenge-response authentication using keys burned into the destination's secure element. Without root-level system integration, the desktop app cannot respond to the challenge, and the setup wizard terminates the source connection with `RESULT_SOURCE_DENIED`.

## Technical Requirements (if YES)
*Not applicable — decision is NO.*

## Fallback Route
**Post-setup standard restore via MTP/ADB.**

After the destination phone has completed its initial setup flow, the user can:
- Connect the source phone to the desktop.
- Use MTP (Media Transfer Protocol) over USB to copy supported file categories (photos, videos, audio, documents, downloads).
- Use ADB (`adb backup`) for supported app data that exports via the Android `BackupManager`.
- A persisted manifest records paths, sizes, checksums, and per-item status.
- Restore is performed by reversing the copy path: desktop → destination via MTP/ADB, with checksum verification at each step.

## Evidence
This determination is supported by the three AOSP source citations in `docs/evidence-catalog.md` (Citations 1–3), which collectively demonstrate that source-role eligibility at setup time depends on USB gadget configuration, DeviceSetupToken possession, and proprietary credential handshakes — none of which are accessible to a third-party desktop application.

## Decision Impact
The product proceeds with a standalone backup/restore MVP. The virtual-source capability is deferred until such time as Google or an OEM publishes a documented, supportable source-role protocol for desktop participation at setup time.
